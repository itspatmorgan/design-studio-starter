Create a working local studio for a designer or product manager. Handle technical steps yourself. Their repository is their source of truth and remains usable without this plugin.

Avoid duplicate setup exploration: read these instructions, the helper, and only required references once. Batch independent prerequisite and registration reads; start Sites registration as soon as the destination is reserved while dependencies prepare. Use the bootstrap helper for tool selection and all follow-up commands; it probes Git execution, preserves pinned Node, and saves a local Git-only shim before preview or publishing. Never handcraft PATH after mise exec or use system Python for setup JSON edits. Use Node. Do not clone the source again when a verified registered checkout is already available.

## First run

1. After plugin activation, follow [Environment audit and installation location](references/local-setup.md). Run read-only `preflight` and inspect host context, available tools, and permissions. Report what you can determine and any uncertainty about where files live. Remote or Ubuntu indicators require explanation, not a guessed laptop path or an automatic rejection. Never create the studio in the plugin cache, a worktree, or a temporary directory.
2. Use the supplied name and location when available. Otherwise use **Design Studio** and read-only `choose` to recommend an available absolute folder under the observed home: Developer on macOS, Projects on Windows/Linux. Display names retain spaces; additional folders are numbered. Share the audit findings and exact destination, then ask the person to confirm or change it before creation. Their response after seeing the audit supplies confirmation; do not ask again. The name can change later. Do not require GitHub, a design system, or product context to launch.
3. Locate the [bootstrap helper](../../scripts/bootstrap.mjs) and inspect Git, Node, and mise. Handle missing tools through supported host mechanisms and official sources in the agreed environment. Use the host's folder-permission flow when required or help choose an accessible folder. Do not assume administrative access or ask the person to run terminal commands.
4. Save the checked name, exact confirmed destination, audit observations, and actual user response with `plan` as described in the setup reference. Keep its JSON file outside the studio and preserve it in restart/activation handoffs. Do not reuse an existing studio for a request to create another one. For interrupted setup, retain its known folder and name. Existing studios without a plugin receipt use open-studio.
5. Run `setup --plan <absolute-plan-json>` to download the pinned starter and prepare the exact planned destination. For interrupted first-run preparation, use `prepare --destination <same-folder> --plan <absolute-plan-json>`. The helper rechecks the environment and destination before creation. Creation selects working-studio files and makes a local Git repository without a remote; its receipt records source provenance. Save detailed output in a local log. Describe progress as **Getting your studio**, **Preparing your studio**, and **Opening your studio**. Preserve the folder and resolve failures; never delete user work to retry.
6. Read the new repository's `AGENTS.md` and required instructions. Personal use and the starter kit are defaults for first-run exploration. Preserve the downloaded starter’s default tagline; change it only when the person requests customization. Follow its setup-contributor procedure for registration. Execute identity and registration commands with `node <installed-plugin>/scripts/bootstrap.mjs exec --destination <folder> -- node scripts/cli/resolve-contributor.js` and, when needed, the same wrapper with `-- pnpm join --yes`. Do not run `pnpm join --help`; it is not a help command in older pinned starters. Use confirmed identity from this session or local configuration; ask in ordinary language if it is missing. Never fabricate names or email addresses. Keep examples available to explore. Explain that Product and Marketing are example systems, and Feedback Inbox and Design Studio Marketing are example prototypes for learning. They should be customized, replaced, or removed to fit the person's needs. Inspect the installed studio before naming examples; omit any that are absent.
7. Start the server through the host's supported local preview/server tools, or run `start --destination <folder>` in an agent-managed persistent local terminal. The person does not need to enter terminal commands. Read Vite's actual loopback URL, since another studio may occupy the usual port. Open it with the host's supported browser/preview capability and inspect the result.
8. Make the real studio folder the working context for continued agent work. Follow [Host handoff](references/host-handoff.md) for Codex desktop, Cursor, or Claude Desktop's local Code view. Do not invent a project API or edit the host's internal database. Opening a preview does not prove workspace opening or persistent project registration.
9. When onboarding includes a request to publish through ChatGPT Sites, continue with [publish-studio](../publish-studio/SKILL.md) after local readiness. Use the same owned folder and return its local preview and public viewing link by default, respecting an explicit audience choice. A publishing failure must preserve the working local studio. Local creation alone remains a local workflow.

Invoke the helper as `node <installed-plugin>/scripts/bootstrap.mjs <command> ...`. Pass arguments individually through a command API, or quote shell arguments safely. `start` also accepts `--port`; do not expose the server beyond loopback.

For a timed journey, follow [benchmark boundaries](../../experiments/benchmarking.md). Measure the entire user wait, including agent work and final handoff, as the primary result.

## Finish

Start the completion message with the local save location in plain language. For example: “Your studio and all its source files are saved on this computer in [actual absolute folder path]. The preview runs locally from that folder. You can find your files there and open them in another editor.” Replace the placeholder with the verified destination. When using the default location, remind them that Developer is simply the folder used to organize their studio files.

Complete tool verification during preparation, then offer the verified workspace handoff and finish promptly after preview/public-link verification. Do not reread host documentation or perform extra cosmetic publication after success unless an unresolved requirement needs it.

Clearly label the bundled systems and prototypes as learning examples in the completion message. Invite the person to explore them, then ask their agent to customize, replace, or remove them for their own needs. Studio is the application system and should be retained. Do not delete examples automatically.

Provide the verified preview URL and workspace handoff. Describe an unclicked link as ready to open, not as completed attachment. All files belong to the person and remain if the plugin is uninstalled. Exploration is ready when the app works; contributor registration is required before creating their own prototype. Configure product context and a custom kit later through the repository's configure-studio skill.

For continued work, use [use-studio](../use-studio/SKILL.md). For prototype work, follow the selected repository's current instructions, resolve the contributor and assigned system, and use its existing commands. GitHub sharing and publishing are separate requests.
